01
SwiftUI internals

View identity, lifetime & dependencies

Why it's asked

This is the single most revealing SwiftUI topic. Bugs like "my state resets", "the animation doesn't run", or "the whole list re-renders" all trace back to identity. If you can explain it, you clearly understand the framework rather than just using it.

Views are descriptions, not objects

A SwiftUI View is a lightweight value — a recipe. SwiftUI calls body, builds a tree of these values, and diffs it against the previous one to update a persistent attribute graph that owns the real render objects and state storage. Your struct may be created and thrown away hundreds of times; that is cheap and expected. What must be stable is its identity, because identity is what state, lifetime, and transitions attach to.

There are three ideas to keep apart:

  • Identity — how SwiftUI knows two values across updates are "the same view".
  • Lifetime — the span during which a given identity exists. @State lives exactly as long as the identity. onAppear/onDisappear and .task are tied to it.
  • Dependencies — the inputs (properties, state, environment, observed objects) whose change causes body to be re-evaluated.

Structural vs explicit identity

Structural identity is the view's position in the type hierarchy. An if/else inside a @ViewBuilder produces a _ConditionalContent<A, B>: the two branches are different views with different identities. Flip the condition and SwiftUI tears one down (state lost, transition out) and creates the other.

Explicit identity comes from ForEach IDs (Identifiable or id: key path) and from .id(_:). Changing a value passed to .id() means "this is a brand-new view" — a sharp tool for resetting state, a footgun when done accidentally.

Stable IDs in lists

AnyView and type erasure

The short version: SwiftUI diffs primarily by type — the static type is the shape of your view tree. AnyView puts the concrete type in a box, so from the outside all SwiftUI sees is "an AnyView". It can no longer know the structure at compile time and has to open the box and compare the real type at runtime on every update.

What some View preserves. some View hides the type from callers, but the compiler still knows it exactly:

What AnyView erases.

Three consequences interviewers want to hear:

  • Identity becomes accidental. State is reset whenever the wrapped type changes — like an if/else, but invisible in the code. The reverse also bites: with @ViewBuilder, if flag { Text("A") } else { Text("B") } gives two distinct identities (each branch of _ConditionalContent, with transitions). With flag ? AnyView(Text("A")) : AnyView(Text("B")), both wrap a Text, so SwiftUI treats them as the same view whose content changed: no transition. Identity now depends on which type happens to be inside at runtime, not on the structure you wrote.
  • Performance. A dynamic type check on every update, an extra box allocation, and no generic specialisation or inlining. It is worst in List/LazyVStack: lazy containers need to cheaply know how many views each ForEach element produces and what their identities are. Apple's WWDC sessions ("Demystify SwiftUI" and the later performance talk) explicitly advise against AnyView in list rows.
  • Debuggability. "Why did my state / animation disappear?" becomes much harder to answer because the deciding information only exists at runtime.

When AnyView is legitimate. When you need real runtime heterogeneity that cannot be known at compile time: plugin registries or server-driven UI ([String: () -> AnyView] chosen by a JSON payload), module-boundary APIs that shouldn't leak generic parameters, or storing views of different types in an array or property. any View doesn't conform to View and can't be returned from body directly, so AnyView is still the tool for these. Keep it at a high-level, rarely changing boundary (e.g. a whole screen), never in list rows or frequently updated leaf views.

One-breath answer"AnyView erases the view's static type. SwiftUI relies on that type to understand structure and derive structural identity at compile time. With AnyView, it has to compare the wrapped type dynamically on every update. If the type changes, the subtree is torn down and recreated, so state is lost and there's no smooth animation. It also blocks compiler optimisations and hurts lazy containers. I prefer @ViewBuilder, some View or generics, and keep AnyView for genuine runtime heterogeneity, like server-driven UI, at a stable high-level boundary."

What triggers body

SwiftUI re-evaluates body when a dependency changes: a stored property passed from the parent differs, a @State/@Binding changes, an environment value it reads changes, or — with @Observable — a property it actually read during the last body call changes. Re-evaluating body is not the same as re-rendering pixels; SwiftUI still diffs the result. The debug helper Self._printChanges() inside body prints which dependency caused the update.

TrapDoing work in a view's init (network calls, creating view models with side effects) runs every time the parent's body runs. Initializers must be cheap and pure; do side effects in .task, which is tied to lifetime and cancelled automatically.

Likely questions

Why does my @State reset when the parent updates?

Because the view's identity changed. Usual causes: it's in a different branch of an if, it's inside a ForEach with unstable IDs, someone applied .id() with a changing value, or it's wrapped in an AnyView whose underlying type changed. @State storage is owned by the attribute graph and keyed on identity, not the struct instance — the struct is recreated all the time and that's harmless.

What's the difference between onAppear and task?

.task starts an async task when the view's identity appears and cancels it automatically when it disappears. .task(id:) additionally cancels and restarts when the id value changes — ideal for "reload when the selected item changes". onAppear is synchronous and gives you no cancellation, so you must manage any Task yourself. Note that both may fire more than once (e.g. in tab views or navigation), so loading should be idempotent.

When would you deliberately use .id()?

To reset all local state of a subtree when its "subject" changes — e.g. a form editing a different user, or resetting a ScrollView position. I'd document it, because it also discards transitions and in-flight tasks, and it's expensive for large subtrees.

Data flow

State management & the Observation framework

Why it's asked

Every screen depends on it, and the toolset changed significantly with iOS 17's @Observable. Interviewers want to see that you know which property wrapper owns data versus which merely references it, and that you've migrated off ObservableObject thoughtfully.

Ownership is the organising question

ToolOwns?Use for
@StateYesLocal value state, and (iOS 17+) owning an @Observable model instance.
@BindingNoTwo-way reference to someone else's value state.
@BindableNoCreate bindings ($model.name) into an @Observable object you were handed.

How @Observable differs from ObservableObject

ObservableObject exposes a single objectWillChange publisher. Any @Published change invalidates every view observing the object, even if that view never reads the changed property. The @Observable macro instead rewrites stored properties to go through an ObservationRegistrar; SwiftUI records which properties each body read (via withObservationTracking) and only invalidates views that read the changed property. Result: finer-grained updates, no @Published boilerplate, and it works on nested/optional/collections of observable objects.

The @State + reference type subtlety

With @StateObject the autoclosure ensured the object was created once. With @State private var model = Model(), the initializer expression is evaluated every time the struct is initialised, though SwiftUI keeps only the first instance. If Model.init is expensive or has side effects, that is wasted work. Options: keep inits trivial, create the model lazily in .task, or inject it from the parent.

Single source of truth

Every piece of data should have exactly one owner; everything else derives or references. Copying a value into local @State in init (_text = State(initialValue: model.text)) creates a second truth that silently stops syncing — a classic senior-level code-review catch.

Senior signalMention that Observation is not SwiftUI-specific: withObservationTracking and (Swift 6.2) the Observations async sequence let UIKit code or services observe the same models, which makes gradual migration from Combine practical.

Likely questions

@StateObject vs @ObservedObject — what goes wrong if you mix them up?

If a view creates an object with @ObservedObject var vm = VM(), a new instance is created every time the parent re-renders the view, wiping state and potentially restarting network calls. The view that creates it must use @StateObject (or @State with @Observable); children that receive it use @ObservedObject (or a plain property).

How would you migrate a large app from ObservableObject to @Observable?

Bottom-up and per feature: convert a model, replace @Published with plain vars, @StateObject → @State, @ObservedObject → plain property or @Bindable, @EnvironmentObject → @Environment(Type.self). Watch for Combine pipelines relying on $property publishers — replace with Observations/async or didSet. Gate on the deployment target (iOS 17). Verify with _printChanges that update counts drop.

Why is a struct-based view model sometimes a bad idea?

View models usually need identity and shared mutable state across async work — a struct copied into closures and tasks would diverge. Value types are great for the state (a struct ViewState), held by a reference-typed owner.

03
Language

Swift Concurrency & data-race safety

Why it's asked

Swift 6 made data races compile-time errors. Teams are mid-migration and need people who can reason about isolation, Sendable, and actor reentrancy — not just sprinkle @MainActor and @unchecked Sendable until it compiles.

The building blocks

  • async/await — suspension points are explicit (await). A suspended function frees its thread; it may resume on a different one.
  • Structured concurrency — async let and TaskGroup create child tasks bound to the parent's scope: they're awaited, cancelled with the parent, and errors propagate.
  • Unstructured tasks — Task { } inherits actor isolation and priority; Task.detached inherits nothing. Both must be managed (stored, cancelled) manually.
  • Actors — reference types that serialise access to their mutable state. Calls from outside are awaited.
  • Global actors — @MainActor isolates code to the main thread.
  • Sendable — a type is safe to share across isolation domains (value types of Sendable members, immutable final classes, actors).

Actor reentrancy — the senior question

Actors are reentrant: while an actor method is suspended at an await, other calls can run on that actor. State you checked before the await may be stale after it. That prevents deadlocks but creates logical races.

Isolation in SwiftUI apps

View is @MainActor-isolated, so body and your view's methods run on the main actor. View models that drive UI should be @MainActor. In Swift 6.2 "approachable concurrency", new app targets can opt into default main-actor isolation, and nonisolated async functions run on the caller's actor by default (nonisolated(nonsending)); use @concurrent to explicitly move work off the actor. Know these settings exist and what they change — it shows you track the language.

TrapsCancellation is cooperative — a cancelled task keeps running until it checks Task.isCancelled / try Task.checkCancellation() or hits a cancellation-aware API. @unchecked Sendable and nonisolated(unsafe) silence the compiler; each use needs a justification (e.g. a lock-protected class) in a code review. Never block inside an actor with semaphores waiting on async work — the cooperative pool has a limited number of threads and can deadlock.

Likely questions

Task vs Task.detached?

Task {} inherits the current actor isolation, priority, and task-local values. Called from a @MainActor method, its body runs on the main actor (except across awaits to other isolations). Task.detached inherits nothing and should be rare — typically for genuinely independent background work. In modern Swift, prefer making the callee @concurrent or nonisolated rather than detaching.

Is an actor the same as a serial DispatchQueue?

Similar mutual exclusion, but differences matter: actors are reentrant at suspension points (a queue running a block is not), access is checked by the compiler, and actors run on the cooperative thread pool without blocking threads. A serial queue with sync can deadlock; an actor can't, but can suffer interleaving bugs.

How do you bridge a callback API to async/await?

withCheckedThrowingContinuation, resuming exactly once (the "checked" variant traps on misuse in debug). For multi-value sources (delegates, notifications), wrap in AsyncStream with AsyncStream.makeStream(), configure a buffering policy, and use onTermination to tear down the underlying observer.

How did you approach the Swift 6 migration?

Module by module: enable complete concurrency checking as warnings, fix leaf modules first (models → Sendable), mark UI layers @MainActor, convert shared mutable singletons to actors or lock-protected types (Mutex from the Synchronization module), use @preconcurrency import for unannotated SDKs, and only then flip to the Swift 6 language mode. Track the count of warnings as a migration metric.

Runtime

Memory management & ARC

Why it's asked

Leaks and crashes from retain cycles remain among the most common production issues. Seniors are expected to spot cycles in code review, explain weak vs unowned precisely, and debug with the Memory Graph and Instruments.

How ARC works

Automatic Reference Counting inserts retain/release calls at compile time. Each class instance carries a strong count (plus unowned and weak counts in a side table). When the strong count hits zero, deinit runs and the object is destroyed. ARC is deterministic — no GC pauses — but it cannot break cycles: two objects that strongly reference each other never reach zero.

ReferenceRetains?Behaviour when target dies
strongYesKeeps it alive.
weakNoBecomes nil; must be an optional var.
unownedNoAccess traps (crash). Use only when lifetime is guaranteed ≥ the reference.
unowned(unsafe)NoUndefined behaviour. Practically never.

Where cycles hide

Tasks capture self too

A Task closure strongly captures self for as long as the task runs. That is not a permanent cycle (the task ends), but a long-running loop — e.g. for await over an infinite stream — keeps the object alive forever. Either cancel the task in a lifecycle hook (SwiftUI's .task does this for you) or capture [weak self] and re-bind inside each iteration.

Value types and memory

Structs don't participate in reference counting themselves, but a struct holding class references (including Array's heap buffer, String, closures) does retain/release when copied. Large structs with many reference fields can generate significant ARC traffic — an advanced performance point.

Tooling to mentionXcode Memory Graph Debugger (purple "!" for leaks), Instruments → Leaks and Allocations (generation marking: "push and pop a screen 10 times, the generation should return to baseline"), MallocStackLogging, and a cheap trick: a deinit print/log in debug builds for view models.

Likely questions

When is unowned the right choice over weak?

When the referenced object is guaranteed to outlive the reference and you want to avoid optional handling, e.g. a Customer and its CreditCard where the card can't exist without the customer, or lazy var closures that only run while self exists. If there's any doubt — especially with escaping async callbacks — use weak; a crash is worse than an optional.

Do SwiftUI views cause retain cycles?

Views are structs, so capturing self in a view's closures doesn't create a cycle with the view itself. Cycles appear in the reference types behind them: view models storing closures that capture the model, Combine subscriptions stored on the same object, or environment objects that reference each other.

Does [weak self] in every closure solve everything?

No — it's cargo cult if applied blindly. Non-escaping closures (map, forEach, withAnimation) can't cause cycles. And guard let self at the top of a long async closure re-creates a strong reference for the whole remaining duration. Be intentional: weak where an ownership cycle or unwanted lifetime extension is possible.

05
Language design

Value types, protocols & generics

Why it's asked

Swift's type system is where API design happens. Interviewers check whether you understand copy-on-write, static vs dynamic dispatch, and the real cost difference between some and any — the knowledge that separates a framework author from a framework consumer.

Value semantics & copy-on-write

Structs and enums are copied on assignment, which gives local reasoning and thread safety for free. Standard collections (Array, Dictionary, String) store elements in a heap buffer and implement copy-on-write: copies share the buffer until one is mutated, at which point isKnownUniquelyReferenced fails and the buffer is duplicated. Your own structs don't get CoW automatically — you implement it when wrapping a class-backed storage.

Dispatch

  • Static — structs, final classes, methods only in protocol extensions, generic code specialised by the optimiser. Inlinable, fast.
  • V-table — non-final class methods.
  • Witness table — protocol requirements called through a generic or existential.
  • Message — @objc dynamic, needed for KVO/swizzling.

some vs any

some P is an opaque type: one concrete type, fixed at compile time, hidden from the caller. The compiler can specialise and inline. any P is an existential box: it can hold different concrete types at runtime, stored in a 3-word inline buffer (or heap-allocated if larger) with a witness table — dynamic dispatch and possible allocation. Since Swift 5.7, some P works in parameter position as sugar for a generic, and primary associated types allow some Collection<Int>.

Rule of thumbDefault to some/generics; reach for any when you genuinely need heterogeneity or to cut generic propagation at a module boundary. Also know newer tools: ~Copyable non-copyable types for unique ownership, parameter packs (each T) for variadic generics, typed throws (throws(NetworkError)).

Likely questions

Struct or class for a model — how do you decide?

Struct by default: value semantics, thread-safety, cheap equality, works with SwiftUI diffing. Class when identity matters (a shared, mutable entity that multiple owners observe), when you need inheritance or Objective-C interop, when the model is an @Observable / SwiftData @Model, or when copying would be semantically wrong (a file handle, a connection).

Why can't you use a protocol with associated types as a plain type before Swift 5.7?

The compiler couldn't know the associated type, so it couldn't type-check member usage. Swift 5.7 introduced any P with implicit existential opening and primary associated types (any Collection<Int>), which covers most cases that previously needed manual type erasers like AnyPublisher.

Is a struct always on the stack?

No. Location depends on context: structs stored in a class, captured by an escaping closure, boxed in an existential that exceeds the inline buffer, or with indirect enum cases live on the heap. Value semantics is about behaviour, not location.

System design

App architecture & modularisation

Why it's asked

At senior level there's almost always a mobile system-design round: "Design an offline-capable feed", "How would you structure an app for 30 engineers?" They look for clear boundaries, testability, and trade-off reasoning — not loyalty to one acronym.

The patterns, honestly compared

PatternStrengthCost
MV / "just SwiftUI"Least ceremony; @Observable models + environment. Great for small apps.Logic drifts into views; harder to unit test.
MVVMTestable presentation logic; familiar to teams.VMs can become god objects; duplication of state.
TCA / Redux-likeUnidirectional flow, exhaustive tests, explicit effects.Learning curve, third-party dependency, compile-time cost.
Clean / VIPERStrong layering for very large teams.Boilerplate; fights SwiftUI's data flow.

Whatever the presentation pattern, the durable structure is: UI → feature logic → domain/use cases → data (repositories) → infrastructure (network, persistence), with dependencies pointing inward and side effects behind protocols.

Dependency injection that stays testable

Using an enum State instead of separate isLoading, error, orders booleans makes impossible states unrepresentable — a point interviewers like.

Modularisation with Swift Package Manager

  • Split by feature (Orders, Checkout, Profile) plus shared core modules (DesignSystem, Networking, Analytics). Features never import each other; they communicate via interfaces or a router.
  • Interface/implementation module pairs (OrdersInterface, Orders) keep build graphs shallow and enable demo apps per feature.
  • Benefits: incremental build speed, enforced boundaries (internal by default), ownership per team, faster previews and tests.
  • Cost: more public API surface, Package.swift maintenance, resource bundles, binary size from duplicate static linking if misconfigured.

System-design checklist for mobile

When asked to design a feature end-to-end, walk through: requirements & scale → API contract (pagination cursors, ETags) → data model & persistence (SwiftData/Core Data/GRDB, cache invalidation) → offline & sync conflicts → networking (retry with backoff, idempotency keys) → UI states (empty, loading, error, partial) → observability (logging, metrics, crash reporting) → security (Keychain, ATS, certificate pinning trade-offs) → feature flags & rollout → testing strategy.

Likely questions

Is MVVM still necessary with SwiftUI?

It's not required — SwiftUI views plus @Observable models are already a kind of MVVM. What matters is that business logic isn't trapped in body and can be tested without the UI. For simple screens I use a model directly; for complex screens with async flows, validation, and multiple dependencies, a dedicated observable screen model pays off. I'd align with the team's existing convention over personal preference.

How would you design an offline-first feed?

Local database is the source of truth; UI observes the DB. A sync engine fetches pages (cursor-based), upserts into the DB, and records a sync token. User mutations are written locally with a pending status and queued in an outbox with idempotency keys; a background processor flushes the queue with exponential backoff and reconciles server responses. Conflicts resolved by server-wins or field-level merge depending on domain. Use BGTaskScheduler for refresh, and expose sync state to the UI.

07
SwiftUI

Navigation as data

Why it's asked

Navigation is where SwiftUI apps historically broke down. NavigationStack made state-driven navigation workable; interviewers want to see programmatic routing, deep linking, and state restoration handled cleanly.

Core model

NavigationStack(path:) binds the stack to a collection. Pushing is appending, popping is removing; navigationDestination(for:) maps value types to views. NavigationPath is a type-erased path for heterogeneous values; a typed [Route] enum is often clearer and easier to test. NavigationSplitView handles sidebar/detail layouts on iPad and Mac. Sheets, full-screen covers and alerts are also state: .sheet(item:) driven by an optional.

Because Route is Codable, the path can be persisted with @SceneStorage for state restoration (NavigationPath also offers a codable representation).

TrapsPass IDs, not large models, in routes — the destination should fetch/observe fresh data. Don't put navigationDestination inside lazy containers (List, LazyVStack) — it may not be registered when needed. Avoid nesting NavigationStacks inside each other; each tab owns one stack.

Likely questions

How do you handle navigation in a modular app where features can't import each other?

Features expose route types or destination builders through an interface module; the app target (composition root) owns the router and maps routes to feature views. Alternatively, each feature registers a navigationDestination for its own route type on the stack. The key is that only the app shell knows the full graph.

Coordinator pattern in SwiftUI — still relevant?

The idea (centralised flow logic, views don't decide where to go) is still valuable; the UIKit implementation isn't. In SwiftUI a coordinator becomes an observable router owning path and presentation state. In mixed UIKit apps, I'd keep UIKit coordinators and host SwiftUI screens via UIHostingController, passing closures for navigation intents.

Craft

Performance & profiling

Why it's asked

"The list scrolls badly — what do you do?" is a favourite because it tests method, not trivia. Seniors measure first, then fix the actual bottleneck: body invalidation, layout cost, main-thread work, images, or launch time.

A diagnostic method

  1. Reproduce on a real, older device in a Release build. Simulator and Debug numbers lie.
  2. Instruments: the SwiftUI template (view body counts, update causes, long view bodies), Time Profiler (main-thread hot paths), Hitches/Animation Hitches, Allocations, and App Launch.
  3. Narrow the cause with Self._printChanges(), signposts (OSSignposter) around suspect code.
  4. Fix, re-measure, guard with performance tests (XCTMetric) or MetricKit in production.

SwiftUI-specific levers

  • Shrink the invalidation surface: split big views into smaller ones so a change only re-evaluates the subview that reads it. With @Observable, pass the model down and let each child read only what it needs.
  • Don't do work in body: no sorting, date formatting, or filtering on every evaluation — precompute in the model.
  • Lazy containers: LazyVStack/List for long content; stable IDs; avoid GeometryReader in every row.
  • Equatable views: conforming a view to Equatable lets SwiftUI skip body when inputs are equal (useful when inputs include closures that defeat the default comparison).
  • Avoid broad environment changes: a frequently changing value high in the tree invalidates every reader.
  • Images: decode and downsample off the main thread (CGImageSourceCreateThumbnailAtIndex, UIImage.prepareThumbnail); cache.
  • Expensive effects: blurs, shadows, and masks force offscreen passes; .drawingGroup() flattens complex vector content into a Metal-backed layer.

Launch time

Measure with the App Launch instrument and XCTApplicationLaunchMetric. Reduce dynamic frameworks (merge or make static), defer non-critical SDK initialisation until after first frame, avoid heavy work in App.init and static initialisers, and lazily load features. Mention pre-main vs post-main phases.

Likely questions

The feed stutters while scrolling. Walk me through it.

Reproduce on an older device in Release. Record with Instruments' SwiftUI and Hitches templates. Typical findings: rows re-evaluated because a parent-level state changes (fix by moving state down / splitting views), synchronous image decoding on the main thread (downsample in background, cache), expensive date/number formatters created per row (cache formatters or use FormatStyle), unstable IDs causing row recreation, and heavy shadows (use shadowPath-style shapes or prerendered assets). Verify the hitch ratio improves, then add a regression check.

Does re-evaluating body mean the view is redrawn?

No. Body evaluation produces a new description; SwiftUI diffs it and only updates render state that actually changed. But body evaluation is not free — excessive evaluations of complex bodies show up as main-thread time, so you minimise unnecessary ones.

SwiftUI

Layout system & animation

Why it's asked

Building custom, pixel-perfect UI is daily work. Understanding the proposal-based layout algorithm and the transaction-based animation model is what lets you build without fighting the framework — and explain why GeometryReader "breaks" layouts.

The three-step layout dance

  1. Parent proposes a size to the child (ProposedViewSize: width/height may be nil = ideal, 0 = minimum, .infinity = maximum).
  2. Child chooses its own size. The parent must respect it — children always decide.
  3. Parent places the child in its coordinate space, using alignment.

This explains much: Text sizes to fit its content; Color and Shape are greedy and take the whole proposal; .frame(width:) is a new parent view that proposes a fixed size; modifier order matters because each modifier wraps the previous view (.padding().background() ≠ .background().padding()). GeometryReader accepts the full proposal and gives its child the size — it's greedy, which is why it inflates layouts. Prefer containerRelativeFrame, onGeometryChange, ViewThatFits, or a custom Layout.

How animation actually works

Animations in SwiftUI are driven by state changes inside a transaction. withAnimation sets an animation on the transaction; .animation(_:value:) attaches one to changes of a specific value in a subtree. SwiftUI then interpolates every Animatable property (via animatableData) between old and new render values. Insertion/removal animate via transitions, which depend on identity — which loops back to Topic 01.

Senior signalMention accessibility: honour @Environment(\.accessibilityReduceMotion), support Dynamic Type by not hard-coding heights, and use ViewThatFits to switch layouts at large text sizes.

Likely questions

Why does .frame(maxWidth: .infinity) sometimes not fill the width?

The frame proposes up to the parent's proposal — if the parent (e.g. a HStack with other children, or a fixedSize() ancestor) proposes less, the frame can't exceed it. Also alignment: the frame grows but its content stays its own size, aligned centre by default; set the background after the frame to see it.

How do you animate a custom shape or a number?

Implement animatableData (an Animatable property, using AnimatablePair for multiple values) so SwiftUI can interpolate. For numbers in text, use .contentTransition(.numericText(value:)). In iOS 18+, the @Animatable macro reduces boilerplate where available.

Quality

Testing strategy & Swift Testing

Why it's asked

Seniors set quality standards for the team. Expect questions about what to test, how to test async code, how to keep UI tests from flaking, and your familiarity with Apple's newer Swift Testing framework.

The pyramid, applied to iOS

  • Unit tests (most) — models, reducers, view models, parsers, repositories with fakes. Fast and deterministic.
  • Integration tests — real persistence stack in-memory, networking with URLProtocol stubs.
  • Snapshot tests — visual regressions of SwiftUI views across Dynamic Type, dark mode, locales.
  • UI tests (few) — critical journeys (login, purchase), with launch arguments to stub the backend and accessibility identifiers for stable queries.

Swift Testing

Introduced with Xcode 16: @Test functions, #expect and #require macros with rich failure output, @Suite types (a fresh instance per test, so init replaces setUp), parameterised tests via arguments:, traits (.tags, .disabled, .timeLimit, .bug), and tests run in parallel by default. It coexists with XCTest; UI and performance tests remain XCTest.

Making code testable

  • Inject dependencies (network, clock, UUID, date, persistence) instead of reaching for singletons. Injecting a Clock makes debounces and timeouts testable without real waiting.
  • Keep logic out of views; test the model that drives them.
  • Async tests: await the operation directly where possible; for callbacks/streams use confirmation() (Swift Testing) or expectations (XCTest). Avoid sleep-based tests.
  • Flaky UI tests: disable animations via launch arguments, wait on element existence (waitForExistence), reset state per run, and never depend on live backends.

Likely questions

How do you test SwiftUI views themselves?

Mostly indirectly: views should be thin, so I test the observable models they render. For appearance, snapshot tests (e.g. swift-snapshot-testing) on key states and configurations. For behaviour, a small number of XCUITests on critical flows. Previews with fixture data act as living documentation and a quick manual check.

What's your approach to coverage targets?

Coverage is a signal, not a goal. I prefer guaranteeing coverage of the domain and data layers and regression tests for every fixed bug, rather than a global percentage that incentivises testing getters. Track flakiness and test duration too — a slow, flaky suite gets ignored.

Rapid fire

Things you should be able to answer in 60 seconds

AUIKit interop
UIViewRepresentable: makeUIView once, updateUIView on every state change (must be idempotent), Coordinator for delegates. UIHostingController embeds SwiftUI in UIKit; set sizingOptions = .intrinsicContentSize for self-sizing.
BSwiftData & Core Data
@Model classes, ModelContainer/ModelContext, @Query in views. Contexts aren't Sendable — use @ModelActor for background work and pass PersistentIdentifiers across actors. Know migrations (VersionedSchema).
CCombine today
Still fine for streams of events with operators (debounce, combineLatest), but new code favours async sequences and Observation. Know AnyCancellable lifetime, receive(on:), and bridging with .values.
DApp lifecycle
App/Scene, @Environment(\.scenePhase), UIApplicationDelegateAdaptor for push and SDK setup, background tasks with BGTaskScheduler and the .backgroundTask scene modifier.
ESecurity
Keychain for secrets (never UserDefaults), Data Protection classes, ATS, certificate pinning trade-offs, Sign in with Apple / passkeys, jailbreak detection limits, privacy manifests and required-reason APIs.
FAccessibility
Labels/values/hints, traits, accessibilityElement(children: .combine), Dynamic Type, VoiceOver rotor, sufficient contrast. Senior candidates treat it as a requirement, not polish.
GNetworking
URLSession async APIs, typed request/endpoint abstractions, retry with jittered backoff, cancellation, Codable strategies (dates, snake_case), handling 401 refresh with a single in-flight token refresh actor.
HModern platform
Widgets & Live Activities (ActivityKit), App Intents for Siri/Shortcuts/Spotlight, the Liquid Glass design language in iOS 26 (glassEffect), Swift macros, and on-device intelligence via the Foundation Models framework.
ILeadership stories
Prepare STAR stories: a migration you led (UIKit→SwiftUI, Swift 6), a production incident you debugged, a disagreement on architecture, mentoring a junior, and a trade-off you'd make differently now.
